```

├──────────────────────────────────────────────────────────┤

├──────────────────────────────────────────────────────────┤

│   hash/         md5 sha1 sha2 sha3 blake2 blake3 crc       │
│   b64.rs        Base64                                     │
│   pattern.rs    通配符匹配 + 捕获                          │
│   template.rs   %占位符模板渲染                            │

│   natsort.rs    自然排序                                   │
├──────────────────────────────────────────────────────────┤
│ util/           io 缓冲、字节序读写、变长整数、hex、时间格式化│

```

依赖方向严格单向：`cli → cmd → plan → fsx/archive → algo → util`。`algo` 不许出现 `std::fs`。

## 2. 关键设计决策

### D1 为什么敢零依赖

用户要求算法全部自研。可行的前提是：本项目需要的算法都有公开规范（RFC 1951/1952、LZMA SDK 规范、7z 格式说明、FIPS 180-4/202、RFC 4648、BLAKE3 规范）。**唯一例外是 RAR 压缩**——规范未公开，因此只做只读 store 条目（见需求 §1.2）。

### D2 压缩后端统一抽象

```rust
trait ArchiveWriter { fn add(&mut self, path: &Path, data: &[u8]) -> Result<()>; fn finish(self) -> Result<()>; }
trait ArchiveReader { fn entries(&self) -> &[Entry]; fn read(&mut self, idx: usize) -> Result<Vec<u8>>; }
```

不同的只是"条目数据用什么编解码器 + 容器怎么排布"：

| 格式 | 容器 | 条目编解码 |
|---|---|---|
| zip | 本地头 + 中央目录 + EOCD | store / deflate / bzip2(仅读) |
| 7z | SignatureHeader + Header(可编码) | LZMA2 单 Folder 链 |
| tar | 512 字节 ustar 头 | 无（原样） |
| gz | 10 字节头 + 尾 8 字节 | deflate |
| xz | 流头 + 块 + 索引 + 流尾 | LZMA2 |

大文件不整读内存：`ArchiveWriter::add` 走 `Read` 流，压缩器是流式状态机；`ArchiveReader::read` 返回 `Read` 实现（`zip` 的 deflate 流式解压）。

### D3 压缩器状态机（流式、可增量）

```
Deflater: 输入块 → LZ77(hash chain, 32KB 窗口) → Huffman(动态/固定) → 位流输出
Inflater: 位流 → Huffman 解码 → 回填窗口 → 输出块
LzmaEnc : 输入块 → BT4/HC4 匹配 → RangeEncoder → 输出
LzmaDec : 输入块 → RangeDecoder → 状态机 12 态 → 输出
```

统一接口 `fn push(&mut self, in: &[u8], out: &mut Vec<u8>) -> Result<()>`，`finish` 收尾。这样 GB 级文件内存恒定。

### D4 计划与执行分离

所有破坏性命令都先产出 `Plan { items: Vec<PlanItem> }`：

```rust
struct PlanItem { src: PathBuf, dst: Option<PathBuf>, action: Action, size: u64, note: Option<String> }
enum Action { Delete, Trash, Copy, Move, Rename, Overwrite, Skip }
```

之后依次经过：`护栏检查 → 打印摘要 → 确认（TTY 且非 -y）→ 串行/并行执行 → 汇总`。dry-run 就是在确认点之前返回。

好处：dry-run 与真实执行走同一条代码路径，预演结果可信；护栏只有一处。

### D5 两阶段重命名

链式改名必须有中间态。做法：

1. 所有源先改到同目录 `.wsak_tmp_<pid>_<序号>`；
2. 全部成功后再改到目标名；
3. 步骤 2 任一失败 → 尽力回滚已改项（临时名 → 原名）；
4. 进程崩溃残留的 `.wsak_tmp_*` 在下次启动时清理（仅清本机 PID 且 mtime > 1 小时）。

### D6 并行模型

用 `std::thread::scope`（不引 rayon）实现固定大小工作池：

- 文件级并行：`cp`/`hash`/`unpack` 条目——按 `jobs` 切分，`AtomicUsize` 取任务，结果返回到 `Mutex<Vec<Result>>`。
- 单文件内部不并行（压缩是顺序流，收益低于复杂度）。
- 进度计数用 `AtomicU64`，主线程每 100 ms 刷新一次，避免锁竞争。

### D7 错误模型

```rust
enum Fail { Io(PathBuf, io::Error), Unsupported(String), Guard(String), Usage(String), Corrupt(String, u64) }
```

- 单个条目失败 → 记入汇总，继续下一个（需求 §7.2）。
- 命令返回 `Summary { ok: usize, skipped: usize, failed: Vec<Fail> }`，退出码由 `Summary` 决定（0/1）。
- `Fail::Unsupported` → 退出码 5（RAR 私有方法、AES 加密等）。
- `Fail::Guard` → 退出码 4。

### D8 非 UTF-8 路径

全程 `Path`/`OsStr`。需要显示时用 `to_string_lossy()`（只影响显示，不影响操作）。Windows 下读写用 `std::os::windows::ffi` 的原生 API；Linux 下 `OsStrExt::as_bytes()`。不经过 `str` 中转，因此 emoji/GBK 文件名都安全。

### D9 终端与 JSON 双通道

`term::Out` 有两个实现：`HumanOut`（彩色、进度、表格）与 `JsonOut`（每完成一项 push 一个对象，结束时输出汇总数组）。二者都实现同一 trait，命令代码不感知。非 TTY 自动降级为无颜色、无进度。

## 5. 实现回填（落地后与设计的差异）

这一节是**事后补的**：记录真正写完后与上面设计不一致的地方，以及踩出来的坑。
设计文档保持原样，差异在这里说明，避免"文档好看、代码另一回事"。

### 5.1 实际目录结构

```
src/
├── main.rs                # Cli::parse + cmd::dispatch + process::exit
├── lib.rs
├── cli/mod.rs             # clap derive（含 debug_assert 回归测试）
├── cmd/
│   ├── mod.rs             # dispatch / Global / Filter / expand_targets / walk_relative
│   ├── fsops.rs           # rm cp mv rn touch link
│   ├── inspect.rs         # find stat tree wc dedup
│   ├── archive_ops.rs     # pack unpack split join
│   ├── codec_ops.rs       # b64 hash replace
│   └── config_ops.rs      # cfg
├── plan/mod.rs            # 原设计要拆 select/guard/execute，实际合并在一个模块
├── fsx/mod.rs
├── archive/{mod,zip,sevenz,tar,gz,xz,rar}.rs
├── codec/{bitio,deflate,lzma,lzma_enc}.rs
├── algo/{hash,blake,b64,pattern,template,natsort,regexlite}.rs
├── term/mod.rs
└── util/mod.rs
tests/interop.rs
```

与设计的两处偏差：

1. `plan` 没有拆成 `select/guard/execute` 三个文件。三者的状态高度耦合
   （`Plan` 同时承载动作列表、确认阈值、执行结果），拆开后到处 `pub(crate)`，
   反而更难读。合并为 `plan/mod.rs`（约 700 行）。
2. `codec` 里 LZMA2 分成 `lzma.rs`（解码）与 `lzma_enc.rs`（编码）两个文件，
   因为编码器（匹配 + range 编码）与解码器几乎没有共享代码。

### 5.2 关键改动：遍历接口返回元数据快照

原设计里 `walk_dir` 只返回 `(PathBuf, depth)`，各命令自己 `stat`。
实测 10 万文件时这个设计是致命的：

- 对照实验：Python `os.walk` 纯遍历 0.54 s；加 `os.stat` 变 10.25 s。
  本机**每次 stat ≈ 100 µs**（Defender 实时扫描 + NTFS 元数据）。
- 而 Windows 上 `DirEntry::metadata()` 直接复用 readdir 的 `WIN32_FIND_DATA`，
  **不发起系统调用**。

于是新增 `fsx::walk_entries() -> Vec<WalkItem>`，一次 readdir 带回
`is_dir / is_symlink / len / mtime / rel`。`find`、`tree`、`dir_stats`、`copy_tree`
全部改为消费它。`walk_dir` 保留为薄封装，老调用点不需要改。

效果：`find` 8.8 s → 0.41 s，`tree` 9.6 s → 0.42 s。

### 5.3 SHA-256 加了 SHA-NI 快速路径

纯标量实现约 247 MB/s，达不到需求 §7 的 300 MB/s。实测本机支持 SHA-NI
（`is_x86_feature_detected!("sha")`），于是加了 `shani::block()`：
用 `sha256rnds2 / sha256msg1 / sha256msg2` 指令做轮函数与消息扩展，
状态在 ABEF/CDGH 两组寄存器间重排。这是**借用 CPU 指令**，不是引入算法库，
红线 C-1 依然成立。

- 有 SHA-NI：≈ 920 MB/s
- 无 SHA-NI：自动回落 `block_scalar`（≈ 247 MB/s）
- 两条路径由单测 `shani_matches_scalar` 强制比对（覆盖多块、整块、半块、空输入）

### 5.4 复制过滤下沉到 `CopyOpts`

原设计里 `cp` 的 `-p/--include/--exclude` 只作用于顶层参数，复制目录时不起作用。
落地时把 `include/exclude`（`Vec<Pattern>`）放进 `CopyOpts`，`copy_tree` 的栈元素
改成 `(源, 目标, 相对路径)`，逐条目判断：

- 目录默认放行（否则命中的文件无处安放），除非目录本身被 `exclude` 命中；
- `include` 只约束文件；
- 顶层目录只受 `--files-only/--dirs-only` 约束，名称条件作用在目录内部。

`pack` 同理：顶层目录不再被 `--include` 筛掉（早期的 bug 会产出空归档）。

### 5.5 改名模板：`%d` 是序号，日期另设 `%{...}`

`%d` 在需求里是「序号」（`%3d` 补零），这与 strftime 的「日」冲突。
落地时把日期字段统一放到花括号里：`%{Y} %{m} %{d} %{H} %{M} %{S} %{D} %{T}`，
`%{now:Y}` 表示取当前时间而不是文件 mtime。裸 `%m`（`YYYYMMDD`）保留，与设计一致。

### 5.6 落地时修掉的真 bug（都有回归测试或实测记录）

| 症状 | 根因 |
|---|---|
| 一运行就 panic：`alias "find" is duplicated` | `Find` 上挂了与命令名相同的 `visible_alias`，clap 只在 debug 构建断言 |
| `rm --trash` 引用了不存在的 `force` | `conflicts_with` 指向未定义的参数 |
| `pack -p` 语义歧义 | `-p` 同时被「密码」和「模式」占用；统一为 `-p`=模式、密码用 `--password` |
| `pack --exclude` 与 `SelectArgs` 重名 | 同一参数名定义两次，后者永远为空 |
| `rn -n` 什么都不显示 | `Action::Rename` 的跳过写在了 dry-run 判断之前 |
| `cp dir/ -p '*.jpg'` 整目录被跳过 | 顶层用完整 `accepts` 判断，目录不匹配模式 |
| `cp --flat` 不拍平 | 目标仍拼了 `base_name`，等于没拍平；改为逐文件放进目标目录 |
| `%u` 恒为 `0000` | 渲染时随机串是写死的占位值，改成时间+pid 播种的 xorshift |
| `pack --include '*.txt' proj` 产出空归档 | 同上；空归档还应直接报错而不是写个 22 字节 EOCD |
| `replace 'src/*.rs'` 报 os error 123 | 没走通配展开，把 `*` 当字面路径 |
| `rn photos/ -t ...` 不改里面的文件 | 目录参数没有展开成子项（现在默认展开，`--include-dirs` 才改目录本身） |
| `b64` 输出到终端后提示符粘连 | 单行模式缺结尾换行 |
| `cp --preserve-perms` / `--copy-links` 无效 | 参数解析了但没接线到 `CopyOpts` |
| `touch -m/-a` 不区分 | `Action::Touch` 只有一个时间字段，改为 mtime/atime 各自 `Option` |
| `rm --trash` 报 SHFileOperation 124 | `canonicalize` 的 `\\?\` 前缀 Windows API 不接受 |
| zip `-l 0` 打包出 112 字节空归档 | 仅存储分支把 payload 写成了空 `Vec` |

其中「clap 定义类」的 5 个问题，是一条 `Cli::command().debug_assert()` 测试
一次性暴露出来的——release 构建不做这些断言，只在测试里能抓到。
