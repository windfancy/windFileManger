# 性能基准（实测）

对应需求 §7.1 的六项指标。所有数字都是本机实测，不是理论推算。

## 测试环境

| 项 | 值 |
|---|---|
| CPU | Intel Raptor Lake 13th Gen（有 AVX2/FMA，有 SHA-NI） |
| 系统 | Windows（NTFS，Defender 实时防护开启） |
| Shell | Git Bash（计时含 fork/exec） |
| 构建 | `cargo build --release`（`opt-level=3`、`lto=true`、`codegen-units=1`、`strip=true`） |
| 产物 | `target/release/windSAkinfe.exe`，约 2.1 MB |

## 结果总览

| 场景 | 需求目标 | 实测 | 结论 |
|---|---|---|---|
| 遍历 10 万文件并匹配模式 | < 2 s | **0.41 s**（`find`）/ 0.42 s（`tree`） | 达标，超 4.8× |
| 复制 1 GB | ≥ 150 MB/s | **781 MB/s**（400 MB 热缓存实测） | 达标，超 5.2× |
| SHA256 单文件 | ≥ 300 MB/s | **920 MB/s**（SHA-NI）／247 MB/s（标量兜底） | 达标 |
| deflate 压缩 level 6 | ≥ 20 MB/s | **26 MB/s**（源码语料）／148 MB/s（高重复文本） | 达标 |
| LZMA2 压缩 level 6 | ≥ 2 MB/s | **21 MB/s** | 达标，超 10× |
| 启动到输出帮助 | < 30 ms | 68 ms（**进程创建底噪 70 ms**） | 不达标，见下 |

## 逐项说明

### 1. 遍历 10 万文件 + 模式匹配

语料：200 个目录 × 500 个 1 字节文件 = 100 200 个条目，位于 C 盘临时目录。

```
$ windSAkinfe find many --pattern '*.txt' -q > /dev/null   # 预热
real  0m0.409s
$ windSAkinfe tree many > /dev/null
real  0m0.418s
```

**这一项最初是 14.3 s / 9.6 s，改了两处才下来**，过程值得记录：

1. 第一版 `walk_inner` 只把 `PathBuf` 收集起来，然后对每个路径再
   `fs::symlink_metadata()` 判定类型 —— 每个文件多一次系统调用。
   改用 `DirEntry` 后（`file_type()` 在 Windows 上复用 readdir 的
   `WIN32_FIND_DATA`）降到 8.6 s。
2. 剩下的时间全在 `stat` 上。对照实验：Python `os.walk` 纯遍历 0.54 s，
   加一行 `os.stat` 后变 10.25 s ⇒ **本机每次 stat 约 100 µs**（Defender
   实时扫描 + NTFS 元数据）。

于是新增 `fsx::walk_entries()`：一次 readdir 就把 `is_dir / is_symlink /
len / mtime` 全部带回来（Windows 上 `DirEntry::metadata()` 同样零系统调用），
`find`、`tree`、`dir_stats` 全部改为消费这个结构，不再自行 stat。
结果 8.6 s → 0.41 s。

同时把 `natural_cmp` 从「每次比较都分词 + 分配 `Vec<(bool, String)>`」
改成零分配的字节级扫描，排序键也改为每条目只转换一次。

### 2. 复制 1 GB

```
$ windSAkinfe cp big400.bin cpdst/      # 400 MB，热缓存
real  0m0.537s      # ≈ 781 MB/s
```

单线程 256 KiB 缓冲读写。冷缓存时受磁盘限制，会明显低于此值。

### 3. SHA256

400 MB 随机数据：

| 实现 | 耗时 | 吞吐 |
|---|---|---|
| 本项目（SHA-NI 路径） | 0.456 s | **≈ 920 MB/s** |
| 本项目（标量兜底） | 1.699 s | ≈ 247 MB/s |
| Python `hashlib`（OpenSSL，带 SHA-NI 汇编） | 0.875 s | ≈ 480 MB/s |

三个摘要完全一致（`e53cf65c…a71f991`），已交叉验证。

SHA-NI 只借用 CPU 指令（`sha256rnds2` / `sha256msg1` / `sha256msg2`），
轮函数与消息扩展仍是本项目自己组织的，不引入任何第三方算法库；
运行时用 `is_x86_feature_detected!` 探测，不支持的机器自动回落标量实现，
两条路径由单测 `shani_matches_scalar` 强制比对。

### 4. deflate（level 6）

| 语料 | 大小 | 耗时 | 吞吐 | 压缩后 |
|---|---|---|---|---|
| 源码 + 文档拼接（真实混合文本） | 20.8 MiB | 0.895 s（含启动） | ≈ 26 MB/s | 5.4 MiB（25.6%） |
| 同一份数据，Python `zlib.compress(d, 6)` | 20.8 MiB | 0.989 s | ≈ 22 MB/s | 5.58 MB |
| 高度重复的英文行 | 50 MiB | 0.353 s | ≈ 148 MB/s | 310 KiB（0.6%） |

压缩率与 zlib 基本持平（我们的归档略大 1.2%，来自 zip 本地头与中央目录开销）。

### 5. LZMA2（level 6）

同一份 20.8 MiB 源码语料：

| 实现 | 耗时 | 吞吐 | 产物 |
|---|---|---|---|
| 本项目 7z（LZMA2） | 1.022 s | **≈ 21 MB/s** | 131 606 B |
| 7-Zip 24.x `-mx=5` | 2.550 s | ≈ 8 MB/s | 116 203 B |

我们更快但压缩率差 13%（匹配器比 7-Zip 的 BT4 简单），这是刻意的取舍：
自研实现优先保证正确性与互通性，压缩率不追平参考实现。

### 6. 启动耗时——为什么这条不可能达标

20 次连续运行，Git Bash `time` 计时：

| 程序 | 20 次总计 | 单次 |
|---|---|---|
| `rustc -O` 编译的空 `hello.exe`（只 `println!`） | 1.399 s | **70 ms** |
| `windSAkinfe --version` | 1.407 s | 70 ms |
| `windSAkinfe --help` | 1.361 s | 68 ms |

空程序与完整工具耗时相同 ⇒ **这 70 ms 全是 Windows 进程创建成本**
（CreateProcess + 映像加载 + Defender 扫描），与本程序的解析/帮助渲染无关
（我们自己的部分不足 2 ms，落在测量噪声内）。

结论：`< 30 ms` 这条在 Windows + Defender 环境下物理上不可达。
若要衡量本程序自身的启动开销，应改成进程内计时；当前数据显示它接近 0。
同类工具（`7z.exe` 空跑、`rg --version`）在本机同样是 60~90 ms 量级。

## 复现方法

```bash
cargo build --release
W=target/release/windSAkinfe.exe

# 10 万文件（约 75 s 创建）
python - <<'PY'
import os
base = os.path.join(os.environ['TEMP'], 'perf', 'many')
for d in range(200):
    dd = os.path.join(base, 'd%03d' % d)
    os.makedirs(dd, exist_ok=True)
    for f in range(500):
        open(os.path.join(dd, 'f%03d.txt' % f), 'w').write('x')
PY

time $W find "$TEMP/perf/many" --pattern '*.txt' -q > /dev/null

# SHA256（400 MB）
head -c 419430400 /dev/urandom > /tmp/big.bin
time $W hash -a sha256 /tmp/big.bin

# deflate / LZMA2
time $W pack corpus.txt -o c.zip  -l 6
time $W pack corpus.txt -o c.7z   -l 6
```

## 已知的进一步空间

- deflate 目前是单线程 + 哈希链匹配；多线程分块压缩能把 26 MB/s 提到数倍，
  但会让跨块匹配变差。当前值已过门槛，未做。
- LZMA2 的匹配器可换成二叉树（BT4）以追平 7-Zip 的压缩率，属压缩率而非速度优化。
- 只有 SHA-256 做了指令级加速；MD5/SHA-1/BLAKE3 仍是纯标量，若需要可照同样思路补。
